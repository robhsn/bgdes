Mobile wireframes scope summary

Eight tickets across three phases of the mobile experience: app shell, first-time experience, and the returning-user gameplay loop.

01 App shell 2 tickets · always present

App Open & Navigation

Wireframes for app-open state and global navigation.

Open questions

  • App open state: dedicated main screen/lobby, or default straight to the board (e.g. with a game-start modal layered on top)?
  • Navigation pattern: assumption is a bottom tab bar. Where do system actions (logout, ToC, Privacy) live? Hamburger, dedicated options tab, or somewhere else?

Deliverable

  • Wireframe(s) for the app-open state and the nav shell showing tab bar plus where system/secondary actions live.

Connects to

  • Generic UI Patterns·menu/system actions surface (hamburger, drawer, sheet) reuses that pattern
  • Matchmaking & Lobby·if board is default on open, lobby becomes a modal over the board
  • FTUE: Connecting screen·app-open default informs what users land on when they return online

Generic UI Patterns

A generic, reusable pattern for modals and menus across the mobile app.

Open questions

  • General approach: centered alerts vs. bottom sheets/drawers?
  • Provide a single reusable example so FE can apply it consistently across the app.

Deliverable

  • One generic modal/menu wireframe pattern FE can reuse across screens.

Used by

  • App Open & Navigation·for system actions menu
  • Matchmaking & Lobby·if game-start uses a modal-over-board pattern
  • In-Game & Post-Game·in-game settings and end-of-match state
02 First-time experience 4 tickets · one-time onboarding
FTUE sequence 01Auth & profile → 02Tutorial → 03Post-tutorial → 04Connecting
FTUE step 01 / 04

FTUE, Auth & Profile Setup

Wireframes for first-time user experience, authentication screens, and profile setup.

Open questions

  • FTUE flow: logic and steps are described. Need wireframes against current requirements.
  • Account creation: support anonymous/guest immediately (like web) and promote later, or force a registration prompt before they can play?
  • Auth screens & CAPTCHA: wireframes for login and registration. CAPTCHA (Turnstile) must render on all auth actions (anonymous entry, login, register by email). Cannot be skipped, since we share Supabase Auth with web where it's globally enabled. Design must leave space for the widget.
  • Onboarding: how should avatar and display name selection work?

Deliverable

  • Wireframe flow covering FTUE, the anonymous-vs-registered decision point, login, register, CAPTCHA placement, avatar + display name selection.
Note: the broader FTUE flow referenced here is realized through the three FTUE tickets that follow (Tutorial, Post-tutorial, Connecting). This ticket owns the auth and profile portion of that flow.

Related epics

  • BGM-712 (FTUE epic), BGM-687 (Mobile Auth epic).
FTUE step 02 / 04

FTUE: Tutorial screens + assets

All overlay and interaction assets for the interactive tutorial (Steps 3.0 to 3.4). Tutorial runs on top of existing game-board components.

Deliverables

  • Tooltip overlay system: instructional text bubble positioned above or below the board.
  • Tooltip styles (text bubble with instructional copy).
  • Highlight/pulse states for valid move target points.
  • Home board highlight overlay with colored border (Step 3.0).
  • Direction arrow overlay showing movement direction from point 24 toward point 1 (Step 3.0).
  • Tap hint animation for guided moves.
  • Hand/gesture animation assets (hint, idle re-engagement after ~5s).
  • Portrait orientation only. iPhone and iPad breakpoints.

In sequence

  • Previous: FTUE, Auth & Profile Setup·user has authed and set up profile before reaching the tutorial
  • Next: FTUE: Post-tutorial screen·shown after the tutorial completes
FTUE step 03 / 04

FTUE: Post-tutorial screen

Screen shown after tutorial completion. Two buttons, celebratory tone. Copy: "You've got the basics. Time to play for real!"

Deliverables

  • Post-tutorial layout with two buttons: Play Now (primary) and Try Again (secondary).
  • No third option (no lobby/homepage button).
  • Portrait orientation only. iPhone and iPad breakpoints.

In sequence

  • Previous: FTUE: Tutorial screens + assets
  • Next (offline): FTUE: Connecting screen·if user has no network when tapping Play Now
  • Next (online): Matchmaking & Lobby·into the first bot game
FTUE step 04 / 04

FTUE: Connecting screen (offline state)

Reconnecting/connecting screen shown when a user taps Play Now after the tutorial but has no network. Stop-gap until connectivity is restored before the first bot game.

Deliverables

  • Connecting/reconnecting screen layout.
  • Portrait orientation only. iPhone and iPad breakpoints.

Notes

  • Spec says to use the existing reconnecting screen as a stop-gap. This ticket covers whether it needs FTUE-specific adaptation or can be reused as-is.

In sequence

  • Previous: FTUE: Post-tutorial screen·entered from Play Now when offline
03 Gameplay loop 2 tickets · returning user

Matchmaking & Lobby

Wireframes for starting a game (vs AI or P2P) on mobile.

Open questions

  • How does a user start a game vs AI or P2P?
  • If we default to the board on app open, do we use a modal over the board (like web) or introduce a new mobile pattern?

Deliverable

  • Wireframe(s) showing the game-start entry point(s) and AI vs P2P selection.

Connects to

  • App Open & Navigation·app-open decision (lobby vs board) sets the entry context
  • Generic UI Patterns·if game-start uses a modal-over-board pattern
  • FTUE: Post-tutorial screen·first-time users land here after the tutorial when online
  • In-Game & Post-Game·downstream of game-start

In-Game & Post-Game

Wireframes for in-game settings and the post-game state.

Open questions

  • In-game settings: where do settings like auto-move and sound FX toggles live while a match is active?
  • Game finished: what happens when a match concludes? Modal like web, or a different mobile pattern?

Deliverable

  • Wireframe(s) for the in-game settings surface and the match-end state.

Connects to

  • Generic UI Patterns·settings surface and end-state both depend on the modal/sheet pattern
  • Matchmaking & Lobby·upstream entry into in-game; post-game may route back here
Cross-cutting

Threads that run through all of it

  • Portrait orientation only across FTUE tickets, with iPhone and iPad breakpoints called out explicitly.
  • App-open state (lobby vs board) is the most upstream decision. It cascades into Matchmaking (modal-over-board or a new pattern) and into the Connecting screen context.
  • Auth gate (anonymous-first vs forced registration) shapes FTUE order and where CAPTCHA surfaces. Turnstile is non-negotiable and must render on every auth action; design needs reserved space.
  • Modal/menu pattern from Generic UI Patterns directly informs In-Game settings and the Game-finished state. Resolving that one first unblocks the gameplay-loop tickets.
